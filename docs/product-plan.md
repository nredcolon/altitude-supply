# 山海供产品功能与版本规划

更新日期：2026年10月19日。产品定位及分阶段方向经本轮评审继续推进；首批品类、商户、交货点和实际登录方式仍需业务确认。本文作为后续开发与 GitHub 任务拆分的产品依据。

## 本轮评审与近期范围

山海供是面向海外采购商的螺蛳湾选品与供货平台，将商户货源整理成统一商品目录，由平台承接采购需求、匹配供货商并组织报价。商户免费供货，社群及经营赋能独立收费，付费身份不影响准入或分配。

近期交付聚焦 V0.1 有效货盘：真实商户能维护、运营能核实。先建立可配置的品类必填属性、标准国内交货点和自由可供数量确认；用少量真实商户验收后，再进入精简 B1 选品询价。B1 优先精选目录、详情、分享、选品清单和后台承接；复杂专题、多语言、买家账户、支付、独立商户店铺及完整履约系统后续再排。

关键规则：

- 同一 SKU 必须在关键属性、质量和包装上可按同一约定交付；不同规格分别建 SKU。后续 B1 可按商品款式聚合规格展示，询价和匹配仍落到确定 SKU，当前尚未实现款式分组。
- 模板定义由管理员核实后建立，普通运营只读并应用模板，商户填写属性。新模板不自动合并或改写历史 SKU；历史通用字段商品需逐项核实。
- 可供量表示所报交期内可按当前条件提供、且未被山海供订单占用的数量，不等于实时库存或实物锁定。每次维护数量或续期须明确确认，运营代录保留核实依据。
- 不增加逐需求询价任务。客户确认后仍需复核供货并形成供应商执行交接；M1 不承诺已实现数量预占。
- 分享来源用于渠道跟进与贡献记录，供货分配按有效供货条件。分享者不默认获得该询价的供货权；商户自主经营客户及指定货源另行评审。
- 商户侧反馈先显示供货有效性；海外展示和分享状态随 B1、实际供货结果随执行阶段补齐。不将候选匹配次数当作真实订单。

试用重点记录有效货盘覆盖、需求到可用报价耗时、货源变化造成的返工、实际供货完成情况。后两阶段指标在对应功能可用后采集，不用上架量替代业务结果。具体试用准备和验收见[路线图](roadmap.md)。

山海供连接螺蛳湾供货商户与海外采购商，由商户供货端、海外选品端和运营后台共同组成。商户维护商品及供货条件，海外采购商在线发现商品、选品并提交采购清单，平台运营承接需求，系统匹配供应商、组合数量并辅助报价。

首版要完成的业务结果是：**海外采购商能在线找到螺蛳湾的商品并提交采购需求，运营能基于有效货盘，快速确定供货来源、数量、内部成本和客户报价。** 自动匹配覆盖已明确标准 SKU 和供货条件的商品；其他需求进入待确认清单。

## 1 已确认的产品原则

- 产品名称为山海供。平台供货功能对商户免费，收费集中在社群服务和经营赋能侧；付费会员身份不影响准入、匹配排序或分配数量。
- 商户和运营使用两个登录地址、共用一套管理后台，按管理员、运营、商户角色隔离菜单、操作和数据；首版围绕一个统一平台货盘运营。
- 产品包含商户供货端、海外选品端和运营后台。海外选品端纳入首版，客户也可继续通过原有渠道提交需求，由运营代录。
- 供给侧开发顺序保持商户入驻 → 标准 SKU 库 → 商户供货维护 → 自动匹配组货 → 对外报价。海外选品端在货盘基础具备后接入，提供在线需求入口。
- 一个标准 SKU 可以有多个供货商。商品的公共资料与各商户的价格、数量及交期分别保存。
- 商户提前维护有效供货条件。每份采购需求直接使用有效货盘匹配，无逐笔询价和等待商户回复环节。
- 内部供货成本与客户报价分别管理。客户报价不公开商户底价、供应商组合及内部备注。
- 按可验收版本推进，逐步完成商户货盘、海外选品询价、匹配组货和对外报价。

## 2 使用者与权限

| 使用者 | 首版工作 | 可以看到的数据 |
|---|---|---|
| 商户 | 申请入驻、关联商品、维护供货条件、处理退回资料和过期提醒、查看关联商品的海外展示状态 | 平台可关联的标准商品、自家资料、自家供货报价及状态 |
| 运营 | 审核商户和商品、维护对外选品内容、发布商品与专题、承接询价、匹配组货、制作报价、记录客户确认 | 所负责平台空间内的商户、供货成本、采购需求、方案和报价 |
| 管理员 | 管理运营成员、授权、品类规则和平台参数 | 平台配置、成员与操作记录；可兼任运营 |
| 海外采购商 | 浏览与搜索、选择规格数量、加入选品清单、提交询价或找货需求、接收客户版报价 | 已公开的选品资料及专门发给自己的报价；不能查看内部货盘和其他客户询价 |

商户身份由登录账号绑定，运营代录要保留代录人与商户确认依据。账号认领和运营成员邀请、停用已有开发实现，真实试用待完成。默认权限只有管理员、运营、商户三类，不建设自定义角色设计器。

运营登录地址为 `/operations/login`，商户登录地址为 `/merchant/login`。两个入口共用认证和后台服务，登录后分别进入 `/operations`、`/merchant`。身份由服务端授权决定，登录地址不能改变角色。商户只看到自家数据；运营查看统一平台货盘；管理员额外管理运营成员。普通账号不能自行创建运营空间或通过商户页面切换运营身份，平台初始化由部署管理员完成。

海外采购商首期可免注册浏览、选品和提交询价，提交时提供必要联系资料。采购商账号、历史采购中心、站内报价确认和在线支付后续按需求增加。首期沿用平台统一承接、匹配和报价的业务关系，不要求商户自行维护外文店铺和逐条回复客户。

## 3 首版业务流程

供给链路：商户申请并通过审核 → 搜索或申请标准 SKU → 发布有效供货报价 → 运营完善外文内容并发布到海外选品端。

采购链路：海外客户进入商品页或专题货盘 → 选择商品、规格和数量 → 提交采购清单与联系方式 → 后台生成待处理需求 → 运营核对交货条件 → 自动匹配组货 → 制作客户报价 → 记录客户确认版本 → 复核并预占数量 → 导出执行清单。

客户提交图片或表格找货、运营代录线下需求，也进入同一需求队列。选品询价不生成已成交订单，不占用供货数量。

“组货”在首版指供应商和数量的组合。实际货物何时入仓、如何验货和发运，先由现有业务流程执行，系统记录交接结果。

建议首版在报价之后保留最小确认、数量预占和执行交接能力，后续逐步建设备货、实物集货、运输和结算。

## 4 页面与功能清单

### 4.1 商户端

手机优先，导航保持为“首页、我的供货、我的”。已有标准商品的供货应尽量复用公共资料。

| 页面 | 主要功能 | 首次交付阶段 |
|---|---|---|
| 入驻申请 | 登录、店铺名称、经营品类、联系人、联系电话、档口位置、必要证明资料；提交、退回补充、审核结果 | M1 补齐 |
| 供货首页 | 待补资料、已失效及即将到期的报价、有效供货商品数；直达需要修改的商品 | M1 补齐 |
| 我的供货 | 搜索、按有效或待审核等状态筛选；查看和修改价格、可供量、交期；暂停供货 | M1 基础已有，补齐快捷维护 |
| 新增供货 | 搜索标准商品 → 核对规格 → 填供货条件；找不到商品时申请建品 | M1 基础已有，补齐图片上传 |
| 商品与供货详情 | 公共 SKU 信息、自家供货条件、审核意见、更新时间及到期时间；后续显示海外展示状态及商品分享链接 | M1 基础已有，B1 补展示关联 |
| 我的 | 店铺资料、账号归属、平台联系人、操作记录 | M1 补齐 |

快捷维护优先提供“改价格、改数量、改交期、暂停供货”。续期时集中展示现有条件，由商户确认仍然有效后提交；系统不自动延长供货承诺。

商户只需在商品资料变化、供货条件变化或报价到期时维护。每份采购需求不增加商户待回复任务。供货执行任务待 V1.2 再进入商户首页。

| 页面 | 主要功能 | 首次交付阶段 |
|---|---|---|
| 工作台 | 待审核商户、待审核商品及供货关联、失效货盘、新询价、待处理需求与报价 | 随各里程碑补齐 |
| 商户管理 | 建档、审核、退回、暂停、恢复、运营代录、账号认领、查看该商户货盘 | M1 |
| 标准商品库 | 品类与必填属性、商品编码、图片、规格与包装、同款核对、审核和停用 | M1 |
| 供货报价管理 | 按 SKU 聚合查看多家报价，筛选有效性、查看历史变更及代录依据 | M1 |
| 海外商品与专题 | 外文名称与介绍、公开图片与规格、上架审核、分类、专题清单、分享链接、供货失效提示 | B1 |
| 采购需求 | 线上询价及运营代录共用列表；客户资料、附件、多商品清单、来源、负责人、SKU 映射、交货要求 | B1 接单，M2 补匹配字段 |

| 客户报价 | 独立销售单价、币种、费用、交付和付款说明、有效期、预览、版本及 PDF 导出 | M3 |
| 确认与交接 | 记录客户确认版本、复核供货条件、预占与释放数量、导出供应商执行清单、记录交接人和时间 | M3 |
| 基础设置 | 运营成员、品类标准、报价口径、国内交货点、有效期规则和操作记录 | M1 至 M3 按需补齐 |

客户资料在采购需求中维护并可复用，首版只需名称、国家或地区、联系人、沟通方式及目的地，不扩展为销售 CRM。

### 4.3 海外选品端

以适配手机和电脑的网页承接海外访问。首期建议英文界面及英文商品内容，使用实际目标渠道验证；其他语言按渠道逐项增加。商户提交中文商品资料，平台运营负责外文内容准确性。

| 页面 | 采购商操作 | 必要内容 |
|---|---|---|
| 首页与专题货盘 | 按品类、用途或运营专题进入选品 | 平台介绍、螺蛳湾货源说明、商品入口、采购流程、联系平台 |
| 商品列表 | 搜索关键词、按品类和规格筛选 | 商品图片、外文名、关键规格、询价入口、供货待核实提示 |
| 商品详情 | 核对规格和包装、填写数量、加入选品清单 | 对外商品资料、计量单位、规格选择、明确的起订或数量提示、申请报价按钮 |
| 选品清单 | 汇总多个商品、调整规格数量、删除项目 | 对应标准 SKU 的选品行；保留数量单位，不展示推算的交易总额 |
| 询价提交与回执 | 填写公司或商户名称、联系人、国家、目的地、预期采购时间及联系方式 | 至少一种可用联系方式，例如邮箱或带国家代码的 WhatsApp 号码；提交成功返回询价编号和下一步说明 |
| 找货需求 | 提交目录外商品描述、图片或采购附件 | 商品要求、数量、目的地与联系方式；明确为待人工确认的需求 |

首期商品价格入口使用“申请报价”。供货底价不公开，客户询价后由运营生成独立销售报价。以后如需公开参考售价，另设对外价格及有效期，不能从最低供货价直接展示。

选品清单是询价清单，客户无需先开账户。首次回执只确认收到需求，正式报价通过运营核实后的联系方式发送；首期不承诺自助查单，也不通过可枚举编号公开询价详情。

### 4.4 对外商品与实际货源的关系

标准 SKU、商户供货报价和对外商品展示分别管理，避免将内部货盘直接发布到公网。

- 同一标准 SKU 对外展示一份选品条目，背后可匹配多家商户。不同规格对应各自 SKU，可在详情关联切换；每个选品行保存确定的 SKU 和数量。
- 入库审核与对外发布分开。商品资料完整、有经过核实的供货来源、外文内容及图片审核通过后，由运营发布。商户可看到关联商品是否已展示及原因。
- 公开资料使用独立字段清单，不包含供应商底价、内部备注、私人联系方式和分配规则。商户品牌及厂家信息仅在确实构成商品识别资料且允许公开时展示。
- 起订量、数量倍数或参考交期的公开提示必须来自可执行、可追溯的供货条件；不能拼接不同商户的最低起订量、最快交期和最低价格，构造不存在的承诺。暂不能形成统一口径时提示按采购清单核实。
- 所有有效货源失效时，商品标记“供货待核实”，退出可供商品筛选，不继续展示确定的库存和交期。可保留询价入口，提交的需求进入待核实队列。
- 提交询价时再次校验商品及规格；已下架或规格变化的条目要让客户明确修正。询价保留当时公开资料快照，后续商品修改不覆盖客户原始请求。

### 4.5 线上触达与询价跟进

商品页和专题货盘要有稳定的公开链接、清楚的分享预览和搜索可读的页面信息。运营与商户可将商品链接分享给海外渠道；平台制作按品类、用途或客户需求组织的专题货盘，供渠道人员转发使用。

询价保留来源页面、专题或渠道标记，去重后分配运营负责人，工作台提示新需求及超过约定跟进时间的需求。渠道来源仅用于分析和跟进，不改变供应商匹配排序。首期不向商户开放买家私人联系方式或其他供应商数据。

平台需要同步运营已有海外经销商、渠道伙伴、展会与社交渠道，把采购商引入选品页，并持续改善内容和跟进。网站提供发现与提交需求的入口，真实访问和有效询价需要通过运营验证。

## 5 核心数据与状态

| 对象 | 关键内容 | 与其他对象的关系 |
|---|---|---|
| 商户 | 身份与账号、店铺、联系人、品类、档口、准入状态 | 一个商户维护多份供货报价 |
| 标准 SKU | 编码、名称、图片、品类、品牌或来源、型号、材质、规格、质量要求、计量单位、包装 | 一个 SKU 对应多家商户供货 |
| 商户供货报价 | SKU、商户货号、人民币供货单价、价格口径、数量、起订量、数量倍数、交期、国内交货点、有效期、版本 | 一个商户对同一 SKU 维护一份当前报价，保留变更记录 |
| 对外商品及专题 | 标准 SKU、外文内容、公开图片、规格、发布状态、版本、专题和公开链接 | 对外展示与商户报价分离，同款多家供应在内部聚合 |
| 采购需求及明细 | 来源、客户、负责人、原始资料与展示快照、商品描述、SKU、数量、海外目的地、预期到货要求、运营核实的国内交货约束 | 线上询价与运营代录使用同一对象；一份需求包含多条商品，生成多个方案版本 |
| 组货方案及分配 | 需求版本、算法版本、供货条件快照、分配量、内部成本、缺口、排除原因、调整依据 | 每次重算保留独立版本 |
| 客户报价及明细 | 方案版本、客户、独立销售价格、报价币种、费用边界、有效期、条款、发送与反馈记录 | 一个方案可形成多个客户报价版本 |
| 数量预占及交接 | 关联报价、供货报价版本、预占量、状态、到期时间、释放原因、执行交接 | 从客户确认的具体报价追溯到每家供应商的数量 |

建议状态如下：

- 商户：待审核、待补充、已准入、已暂停。
- 标准 SKU：待审核、待补充、已生效、已停用；生效后的商品身份变化需新建 SKU。
- 对外商品：草稿、待发布审核、已发布、已下架；供货待核实状态由当前有效货源计算。
- 供货报价的审核状态：待审核、已通过、已退回、已暂停；“已过期、低于起订要求、商户暂停”等由当前条件计算并显示原因。
- 采购需求：草稿、待确认 SKU、可匹配、已关闭；匹配结果另显示全部满足、部分满足、无法满足，避免把处理状态和匹配结果混为一项。
- 客户报价：草稿、已发送、客户要求修改、客户已确认、客户已拒绝、已过期、已作废；另行显示供货复核、数量预占和交接状态。
- 数量预占：生效、已释放、已失效、已转执行占用、已履行。客户确认不自动代表已经预占成功。

这些状态是后续产品要求，当前 M1 的审核状态较简化，开发时需要补齐迁移与状态校验。

## 6 标准 SKU 与供货维护规则

### 6.1 明确什么是同一款

首批每个品类先确定一份商品字段模板。影响互换性的属性必须完整，例如品牌或来源、材质、型号、尺寸、颜色、质量等级和包装。外观相似只作为人工核对线索，不能直接合并。

商户先搜索已有 SKU，再提交供货条件。新商品由运营审核，可新建 SKU 或关联已有 SKU；选择已有 SKU 时向商户展示明确规格。混色、混码和包装不同的商品，首版按明确规格分别处理。

M1 现有同款指纹只能识别规范化字段一致的建档，真实品类的同款判定仍需运营完成。首版不自动跨 SKU 替换，也不建设图片识货算法。

### 6.2 供货条件必须能直接用于匹配

必填信息包括供货单价、价格口径、可供数量、起订量、数量倍数、交货周期、国内交货点和报价有效期。首次关联需要审核；已审核报价日常改价或改量产生新版本。公共商品属性改变需要重新建品或重新关联。

首版建议统一采用人民币、整数基础单位和可核实的国内交货口径。必须明确单价含不含约定税费和国内送货费用；口径无法比较的报价进入待确认列表。非整数计量、阶梯价、跨 SKU 起订或优惠作为后续扩展。

报价有效期是当前条件可用于匹配和成交复核的期限，交货周期是预期交货所需时间，分别记录。国内交货截止时间与海外到货要求也分别记录；首版算法仅校验国内交货约束，海外到货可行性由运营核实。

## 7 自动匹配与组货规则

### 7.1 先把采购描述变成标准需求

海外选品清单生成需求时携带标准 SKU、数量和公开资料快照。客户填写目的地与期望到货时间；国内交货点和最晚交货日期由运营结合运输安排核实，不要求海外客户理解国内供货规则，也不直接把海外到货日期当作国内交货日期。

运营代录或客户提交找货需求时，保存原始图片、文字或清单，再逐条映射标准 SKU。未能映射的条目保留为待确认，不能在总需求中静默消失。首版支持在线选品、手工录入和附件留存，结构化批量导入放到 V1.1。后台匹配前仍需检查数量单位、商品状态和供货条件。

同一需求内，相同 SKU 且交货条件相同的行先合并数量；条件不同则分别分配，但共享同一货源的可用量，不能把同一批货重复使用。

### 7.2 筛选可参与的供货报价

逐项检查商户、SKU 和供货关系状态；SKU 身份一致；报价未过期；价格口径、质量、包装和交货地点符合要求；可用量与交货周期满足条件。相似款不自动补入。

每家供应商的分配量要么为零，要么达到起订量，并满足数量倍数。匹配读取未被平台订单承诺的自由可供量；数量预占时已扣减的部分不能再次扣减。超交期、过期、数量约束不符等分别输出原因。

### 7.3 选择可执行的数量组合

首版默认优先级建议为：完整满足需求 → 内部供货成本更低 → 成本相同时供应商更少 → 再比较最晚交货时间 → 最后按稳定标识排序。

先在每个 SKU 及明确交货条件内求解，再汇总整份清单。首版不承诺全单供应商数量最少，不计算跨商品运费合并或阶梯优惠；这类条件需要后续增加独立规则。

不能简单按价格从低到高依次取库存。例如需求100件，甲2元/件、起订及倍数60件、最多60件；乙3元/件、起订及倍数100件、最多100件。先取甲60件会使剩余40件无解，但全部选乙100件是可行方案。

精确满足数量为默认要求，不自动多买整箱。无法精确满足时，在不超量的合法组合中优先满足更多数量，再比较成本，标明缺口和数量约束；若接受多买或替代款，运营需明确修改需求并保留客户确认依据。

算法必须有可说明的输入规模和运行边界。超出首版支持规模时显示需人工处理，不把超时误报为无货，不把未经验证的近似方案标为最低成本。

### 7.4 输出方案并允许人工调整

每行显示需求量、分配到各商户的数量、供货单价、交期、内部成本及缺口；同时列出主要排除原因。整单显示全部满足或部分满足，以及未确认商品。

运营可以选用其他合格供应商或调整分配量，系统重新验证起订量、数量倍数、可用量和交期，并要求填写调整原因。重新匹配产生新版本，已发送报价不会随之变化。

首版性能验收目标建议：在约定的试用环境内，一份不超过20行、每 SKU 不超过10家候选、数量不超过每行1000个可分配单位的支持范围内，95%的匹配请求在5秒内返回。通过实测确定并公开最终支持范围；不得以速度目标牺牲约束正确性。

## 8 对外报价与数量管理

### 8.1 内外价格独立

| 内部运营视图 | 客户报价视图 |
|---|---|
| 商户、供货单价、分配量、内部成本、方案版本、运营备注 | 客户、商品图片与规格、采购量、销售单价、金额、币种、费用及条款 |

运营手工填写销售单价及费用，系统计算客户报价合计。首版不自动按供货价加成，不查询实时汇率；客户报价可选择币种，外币价格由运营确认，整份客户报价采用同一币种。人民币成本与外币售价不直接相减计算利润。

每项附加费用明确金额和币种，或明确“未包含、待核实”。待核实费用不能当作零，客户看到的合计必须注明已包含范围。交付范围、付款说明及实际报价主体同时保存。

先提供标准客户报价模板，复用海外选品端经核对的外文商品名，支持双语字段标题。输出预览与 PDF；客户版通过独立字段清单生成，不复用包含供货底价的运营数据。多语种站点及报价模板按目标市场继续扩展。

### 8.2 报价有效期与版本

每次发送保存不可变的商品、数量、售价、费用、条款及供货条件快照，并记录报价编号、版本、发送时间和操作人。发送通过运营现有沟通渠道完成，系统保留发送记录。

客户报价有效期不晚于相关供货报价的最早有效期，还要核对交货周期对应的最晚可确认时间。时间语义统一按北京时间记录并在对外报价中标明。未定义清楚最晚确认时间的需求由运营复核，不能只靠报价到期日推断交货可行性。

客户要求修改时创建新版本。确认记录必须对应具体版本；过期或作废版本不能直接继续采纳。

### 8.3 客户确认后的最小闭环

试算和发送报价不占用数量。运营记录客户确认后，系统核对最新价格、数量、有效期与交期，并核实确认范围。首版整单采纳；客户只接受部分商品时先生成相应的新需求及报价版本。

复核通过后一次性预占整个方案所需数量。同一确认重复提交不重复预占；任一货源不足则整单预占失败，列出变化并重新匹配，不显示全单已锁定。

对数量采用明确口径：商户填写“未被山海供订单承诺的可供量”；预占时扣减自由可供量并新增等量预占记录。商户后续编辑自由可供量不能覆盖预占记录。预占取消或到期时先记录释放，待商户或运营核实仍可供再回补自由可供量，防止外部销售后错误回补。

预占有明确到期时间；交给执行人员后转为执行占用，继续从自由可供量中排除。实际交货记录为已履行，不能在“已交接”时自动释放回库存。取消、失效、释放、回补和执行完成均有记录。

系统管理的是商户申报及平台承诺数量。线下或其他渠道销售发生后，商户仍需更新剩余自由可供量；系统预占本身不代表实物已入仓。

## 9 版本与开发顺序

产品版本表示可交付的业务范围，与当前软件包版本分别管理。保留 M1 货盘、M2 组货、M3 报价的开发编号，新增 B1 海外选品端，交付顺序为 M1 → B1 → M2 → M3。

| 产品版本 | 开发里程碑 | 用户得到的能力 | 进入下一阶段的条件 |
|---|---|---|---|
| V0.1 货盘试用版 | M1 基础与体验补齐 | 商户能入驻、找到或申请 SKU、持续维护有效供货；运营能看到同款多商户货盘 | 真实账号可用；品类同款标准可核实；商户独立完成改价、改量和续期 |

| V0.3 自动组货版 | M2 | 对线上询价和运营代录统一匹配，得到可解释的供应商数量组合和内部成本 | 数量约束及缺口正确；人工核算样本一致；支持范围内性能达标 |
| V1.0 选品到报价闭环版 | M3 | 海外选品、自动组货、客户报价、确认与数量预占、执行交接贯通 | 报价内外隔离、版本不漂移、确认不重复占量、异常可恢复 |

| V2.0 履约与经营扩展 | 后续 | 逐步纳入仓储物流、专业服务协同、收付款、结算和售后 | 以稳定业务和明确责任主体为基础分别立项 |

海外选品与询价是首版能力，客户账户、历史采购、在线确认、在线支付和重复补货按实际使用继续扩展。首版不建设会员付费、自动报关、自动汇兑、智能客服、复杂 CRM 或全套 ERP。

V0.2 可先用于定向获客和收集询价，运营沿用现有人工方式跟进与报价；此阶段不宣称已具备自动组货。V0.3 和 V1.0 逐步将后续处理纳入系统。

| 线上询价进入后台 | 联系资料、SKU、数量、单位、目的地、原始资料快照及来源完整对应，无需重复录入清单 |
| 公开页面和接口 | 不返回内部报价、商户私密联系方式、采购商联系资料或其他询价 |
| 失效货源、商品下架、重复提交 | 状态如实显示，提交时重新校验；重复点击不产生多份相同询价，失败可重试 |
| 海外期望到货时间 | 与国内供货截止时间分开，由运营核实转换，不直接用于错误匹配 |
| 同一 SKU 有两家供货 | 公共资料只有一份，两家各自维护价格和数量，互不可见底价 |
| 商户找不到同款 | 可申请建品；待审核资料不进入可用货盘 |
| 单家足量或多家补量 | 数量精确满足、约束合法、内部成本可复核 |
| 最低单价无法组成合法数量 | 能找到其他可行组合，不因贪心分配误报缺货 |
| 总量不足、包装倍数冲突、未映射 SKU | 部分方案与缺口、原因完整保留，不能显示全部满足 |
| 重复需求行或不同交期使用同一货源 | 全方案分配不超出该货源可用量 |
| 报价过期、商户暂停、交期不符 | 排除并说明原因，不能人工改分配量绕过硬约束 |
| 商户改价或改量 | 历史方案和已发送客户报价不变；采纳时能发现差异 |
| 客户版导出及数据接口 | 不包含供应商底价、内部成本、供应商组合或内部备注 |
| 两份报价并发采纳、同一确认重复提交 | 不超配、不重复预占，失败方案有明确结果 |
| 预占失效、取消、交接、执行完成 | 数量状态可追溯；未核实数量不自动回补；交接不释放占用 |
| 真实商户手机操作 | 能独立登录，新增一份供货，并完成改价、改量、暂停和续期 |

用于人工核对的基本样例：同一 SKU 需500件，5天内交到同一国内交货点。甲9.20元/件、可供400件、3天；乙8.90元/件、可供200件、5天；丙8.60元/件、可供1000件、7天。三家起订和倍数均为100件，费用口径一致。正确结果为乙200件加甲300件，内部商品成本4540元，丙因交期被排除。

### 12.2 建议试用规模与指标

首批建议5至10家商户、2至3个可标准化品类、30至50个标准 SKU，其中至少10个 SKU 能核实两家以上同款供货，邀请3至5位目标海外采购商验证选品和询价，准备不少于10份真实或明确标注的业务演练清单。若同款无法核实，先缩小自动匹配品类范围。

| 指标 | 定义与用途 |
|---|---|
| 商品详情访问到询价转化率 | 统计期内提交询价的去重访客数 ÷ 浏览商品详情的去重访客数；按来源渠道分组，明确统计窗口 |
| 有效询价率 | 经运营核实联系资料可用且采购意图明确的询价数 ÷ 去重询价总数；不把页面访问当作采购需求 |
| 首次跟进耗时 | 询价提交至运营首次实际跟进的时长；首期由运营记录跟进动作 |
| 需求可匹配覆盖率 | 已确认 SKU 且有合格候选供货的需求行数 ÷ 总需求行数；反映货盘是否匹配真实采购 |
| 自动完整组货率 | 无需人工修改即可完整满足的需求单数 ÷ 可进行匹配的需求单数；不足量也保留在分母 |
| 首次匹配到可发送报价耗时 | 从需求完成 SKU 确认至客户版报价可导出的时长；同时记录端到端耗时，避免隐藏人工找品时间 |
| 供货变动重算率 | 因价格、数量、有效期或交期变化需重算的确认单数 ÷ 发起确认复核的单数 |
| 商户维护完成率 | 在试用任务中独立完成规定维护动作的商户数 ÷ 参与试用的商户数 |

权限隔离、数量约束、金额计算、版本追溯和预占并发场景必须全部通过。业务效率指标先建立首批实测基线，再确定改进目标，不用注册数或商品总数替代可执行供货能力。

## 13 平台运营准备

| 工作 | 需要形成的结果 | 最晚准备阶段 |
|---|---|---|
| 选首批品类与商户 | 谁愿意持续维护，哪些商品能确认同款 | M1 试用前 |
| 制定商品标准 | 分品类必填属性、同款判断样例、图片及包装要求 | M1 试用前 |
| 明确供货条件 | 含税及费用口径、国内交货点、报价期限、库存变动与履约责任说明 | M1 试用前 |
| 准备海外选品内容 | 外文名称、规格与单位、可公开图片、专题货盘、平台采购流程和联系说明 | B1 试用前 |
| 组织海外访问与跟进 | 海外试用采购商、分享渠道、渠道标记、负责人及约定跟进时限 | B1 试用前 |
| 整理采购样本 | 原始清单、SKU 映射、数量及交期、人工匹配结果 | M2 验收前 |
| 明确报价与交接方式 | 实际报价主体、模板、销售币种、费用说明、客户确认依据、执行负责人 | M3 验收前 |
| 安排维护责任人 | 商户维护培训、代录确认、过期清理、同款审核、问题跟进 | 全阶段 |

开发可以先推进已明确的入驻、标准商品和供货维护。首发国家、首批具体品类、登录服务及报价币种在对应阶段依据真实试用确定；选品端暂按英文规划，目标渠道需要其他语言时调整内容工作量。沿用原始方案中的泰国渠道作为候选，不把它设为系统唯一国家。
