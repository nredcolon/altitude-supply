# 架构与数据说明

## M1 数据关系

运营空间包含商户、标准 SKU、供货报价及操作记录。SKU 描述平台确认的商品身份；`Offer` 用 `skuId` 和 `merchantId` 关联同款与供货方。供货价格使用整数人民币分，数量使用标准计量单位的整数。

一个商户对一个 SKU 只维护一份当前供货报价，更新递增 `version` 并留下操作记录。M1 操作记录记录变更摘要，不是完整历史快照；M2 匹配结果和 M3 报价必须保存所引用的完整条件快照，不能只存最新报价 ID。

同款指纹使用品类、来源、型号、材质、规格、质量标准、计量单位及包装的规范化值，防止明显重复建档。指纹不是自动商品识别算法；不同写法或潜在同款仍需运营核验。

## 身份与隔离

`app/chatgpt-auth.ts` 读取托管平台注入的可信身份；路由仅把稳定用户 ID 交给应用服务。客户端不得提交角色、运营身份或被操作人的登录账号。

空间创建者为运营负责人。入驻邀请码有效七天，仅保存 SHA-256 摘要；邀请码允许申请成为商户，不允许成为运营。申请者的登录 ID 写入商户记录，后续访问由该绑定关系校验。更新邀请码使旧代码失效，已入驻成员保留关系。

山海供首版按一个统一平台运营。浏览器 API 禁止创建运营空间；初始化仅由部署管理员通过受控数据库操作完成。唯一历史货盘自动沿用；存在多个历史空间时，必须由服务器配置 `SHANHAI_WORKSPACE_ID` 指定其一。未指定或指定不存在时关闭访问，不默认挑选、不合并、不删除。工作台列表、读写、入驻码、认领邀请和图片接口都限制在当前平台内。支持负责人邀请、核实、停用和恢复运营成员，以及代录商户账号认领。尚无负责人转移、已绑定商户换绑或细分运营角色。

托管认证与应用授权是两层控制。当前 Sites 站点仍为未部署的私人站点；真实商户访问前需确定托管访问策略与适合商户的登录体验。GitHub 只是源码维护位置，不提供该应用所需的身份与 D1 数据库。

## 专属邀请与账号交接

`members` 和 `accessInvitations` 为货盘聚合的可选字段，历史记录按空数组读取，不需要改表或重建空间。运营成员的稳定用户 ID 只在服务端保存；负责人可管理成员，普通运营拥有货盘维护和商户审核权限，不能授予运营权限。停用成员立即失去工作空间列表、读写及图片接口访问权，恢复由负责人明确确认。

`/accept#access=<token>` 是专属邀请入口，令牌从地址栏移除后存于当前浏览器会话，以衔接现有登录。系统只保存 SHA-256 摘要，明文仅生成时返回；七天过期。商户认领邀请关联已有 merchantId，运营邀请关联预期受邀人备注。通用入驻码不能替代专属邀请，也不能授予运营身份。

状态流转为 issued → requested → accepted，issued/requested 可撤销为 revoked。收到链接只可查看邀请摘要和填写本人姓名、联系方式，提交申请不授予工作空间访问权。申请人由服务器登录身份绑定，客户端不能指定账号或角色。运营通过原登记联系人核实商户认领；运营成员须由负责人核实。核实确认保存依据，再原子写入账号归属或成员关系；认领不改商户准入状态、SKU、供货价格和版本。核实时重新检查账号冲突、档案归属和邀请有效期。

同一商户重新生成邀请时撤销之前未完成的邀请和申请；已绑定商户不能再次认领。拒绝后需重新邀请，成员停用后恢复走负责人操作。身份冲突、并发申请和撤销/确认竞争由业务校验及空间 revision 比较更新共同保护。邀请摘要、请求者登录 ID 不进入任何客户端货盘响应；普通运营只看商户认领申请，商户看不到成员及邀请列表。历史邀请暂保存在聚合中，扩量前需归档和拆表。

## 写入与并发

`catalog_workspaces` 每行包含一个运营空间聚合，`revision` 用于比较并交换更新。写入前执行业务规则及权限校验，最终用 `WHERE id = ? AND revision = ?` 原子更新；变更与审计摘要同时提交。页面陈旧或并发冲突返回409，不覆盖别人保存的内容。

供货报价还检查 `expectedVersion`，阻止针对旧条件的编辑或审核。业务函数复制输入后变更，失败不污染原状态。成员读模型隐藏其他商户、报价和登录标识。

JSON 聚合使 M1 权限与关联操作保持简单，代价是空间内写入互相竞争、查询需读聚合、事件会占容量。扩大商户或报价规模之前，应拆分 workspace、membership、merchant、sku、offer、offer_version 和 audit_event 表，加索引、分页和迁移脚本。

## 货源有效性

报价必须关联已准入商户、已审核 SKU 和已审核供货关系，并满足有效期及至少一份起订/包装倍数数量。日期按 Asia/Shanghai 的自然日计算。

M1 的“可参与匹配”只是有效性标识，不代表已经执行供应商排序或数量分配。国内交货地点与具体采购需求的匹配留到 M2；海外费用、税费和实时汇率不在该有效性判断中。

## 供货维护与图片

`updateOfferTerms` 只允许已审核供货的价格、可供量、交期或有效期更新；服务端检查商户归属、状态及供货版本。续期要求明确确认原条件，普通改价不续期。运营快捷代录需要核实依据。`updateMerchant` 修改经营资料后回到待审核，保留账号归属并暂停有效供货资格。

商户登录 `/merchant/login`、运营登录 `/operations/login` 共用身份认证。`PortalEntry` 根据服务器身份与当前平台成员关系保护 `/merchant` 和 `/operations`；匿名访问引导至对应登录页，已授权账号走错入口时重定向到自身角色工作台。未入驻账号可以从商户入口填写有邀请码的申请；运营权限只能由平台管理员邀请核实，停用账号不能靠商户入口获得新身份。两个工作台复用 `CatalogApp`，根据真实角色加载菜单及操作。API 独立校验平台、账号、数据归属和操作权限；登录地址或客户端传入的 portal 不授予角色。

新入驻链接使用 `/merchant/login#invite=...`；新专属邀请使用对应 `/merchant/login#access=...` 或 `/operations/login#access=...`。页面在当前浏览器会话保存令牌，移除 URL fragment，登录返回后继续申请；旧 `/accept#access=...` 链接仍可通过两个登录页衔接。正式浏览器中的登录回跳和存储受限场景仍须试用验收。首页只展示已实现的供货入口。

商品图片存入 `BUCKET` 的 `catalog/<workspaceId>/<uuid>`，不把二进制存入货盘 JSON。上传检查登录和准入、5 MB流式上限与 JPG/PNG/WebP 文件特征；不接受 SVG。读取检查空间成员、上传者或已可见 SKU 的关联关系。绑定上传图片到 SKU 前再次校验图片归属及访问权限，避免通过构造 SKU 引用访问他人草稿图片。已生效 SKU 的图片只由运营维护，不修改商品身份指纹。

图片接口使用私有、不缓存响应及 `nosniff`。当前可能有未关联的上传文件，后续按引用核对后清理；B1 公共选品图需单独发布，不能直接将受保护的上传路径当作公开资源。

## 后续模块边界

B1 新增海外公开商品、专题货盘和匿名采购询价入口。对外商品通过标准 SKU 关联内部货盘，使用经过运营审核的公开资料；公共接口不返回商户供货报价或私人联系资料。公共页面可以免登录，商户和运营端继续受权限控制，不能为开放目录而放开整个工作空间。

对外发布、供货有效性分别判断。查询列表、商品详情和提交询价时均校验可用状态；缓存需要失效或设置明确的新鲜度约束，避免供货失效后继续展示有效承诺。询价接收端独立校验 SKU、数量、附件与联系资料，限流并保护重复提交，原子保存询价及回执编号。匿名用户只能得到自己的提交回执，不能按编号枚举询价或客户资料。

线上选品与运营代录共用采购需求对象，保存公开资料快照、渠道来源、客户联系方式和负责人。选品提交不占库存；先由运营核实国内交货约束，再进入 M2。商品页及专题页提供稳定公开地址、可分享摘要及适合搜索读取的内容。买家登录和历史采购中心不在 B1。

M2 复用 B1 采购需求，补齐交货约束核实并新增匹配策略与方案；试算不扣量。匹配函数必须接受明确的 SKU、数量及交货约束，输出数量分配与排除原因，并验证可行解及成本。先约定规则和小规模基准样例，再选具体求解方式。同一方案各需求行共享可用量，求解边界按产品规划明确，不承诺跨 SKU 的全单最优。

M3 新增客户报价、费用项、有效期、完整快照及数量预占。客户读模型由白名单生成，不能复用包含商户底价的运营响应。客户确认具体报价版本后重新复核，数量预占在数据库事务或同一原子写入中完成，并保证重复提交不重复扣量。

数量预占从旧路线图 M2 移到 M3，与客户确认和执行交接一并验收。采用自由可供量与预占、执行占用分离的台账；商户更新自由可供量不能覆盖已承诺数量。取消或失效只释放承诺记录，核实仍可供后再回补；交接转执行占用，不自动回补。详细口径见[产品规划](product-plan.md)。
