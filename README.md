# 山海供

山海供连接螺蛳湾供货商户与海外采购商，规划由商户供货端、海外选品端和运营后台组成。商户提供货源，海外采购商在线选品并提交需求，平台统一匹配组货和报价。

供给侧按“商户入驻 → 标准 SKU 库 → 商户供货维护 → 自动匹配组货 → 对外报价”逐步建设；海外选品端在货盘基础具备后接入，支持商品展示、选品清单和询价提交。

一个标准 SKU 对应多个商户供货报价。商户维护供货价、可供量、起订量、数量倍数、交期及有效期；内部供货成本与客户售价分开管理。供货平台对商户免费，付费社群身份不影响供货资格或匹配排序。

## 当前交付 M1 双入口统一后台

本阶段实现商户与标准货盘基础，海外选品端、自动数量分配及客户报价均待开发。

- 一个统一平台货盘，由管理员在部署侧初始化；普通账号不能创建运营空间。现有商户与供货记录继续沿用。
- 商户凭邀请码申请入驻，登录账号绑定到自己的商户；运营审核或暂停。
- 运营可以协助登记、维护尚未绑定账号的商户。
- 标准 SKU 录入、商品身份校验、审核；同一 SKU 的公共资料不含商户价格和库存。
- 多家商户关联同一 SKU，各自维护供货价、可供量、起订量、数量倍数、交期和报价有效期。
- 首次供货关联审核；已审核关联更新价格与数量产生新版本；下架后再次提交须审核。
- 过期、未准入、未审核或可供数量不足的报价不会显示为有效供给。
- 服务端根据登录账号判断权限，不接受客户端角色声明；商户看不到其他商户报价。
- 操作记录、报价版本、并发冲突保护、桌面与手机界面。
- 商户登录 `/merchant/login`、运营登录 `/operations/login`，工作台分别为 `/merchant`、`/operations`；共用认证、后台组件、业务服务和数据库。角色由服务端账号关系决定，走错入口会引导到对应工作台。
- 商户界面不出现运营注册、建立空间或空间切换；平台管理员管理运营成员，运营维护全平台货盘，商户只维护自家供货。
- 入驻与专属认领邀请从对应登录入口继续办理，保留通用 `/accept` 认领入口以兼容已有链接。
- 商品图片上传至 R2；支持 JPG、PNG、WebP，最大5 MB，图片按运营空间及可见商品权限读取。
- 快捷改价、改量、改交期、确认续期；运营快捷代录必须记录核实依据，过期报价改价不自动续期。
- 首页真实待办、供货有效性筛选与3天到期提醒；商户经营资料修改后重新审核。

- 运营代录商户可通过专属邀请申请认领，运营核实后绑定原商户，保留供货及审核记录。
- 负责人邀请、核实、停用和恢复运营成员；普通运营仅可管理商户认领，不能授予运营权限。
- 专属邀请七天有效、可撤销，重发商户邀请使旧链接失效；令牌只存摘要，申请与核实原子提交。

## 本地运行

使用 Node.js 24 与 npm。在独立项目根目录执行：

```sh
npm ci
npm run build
```

首次使用一个新的本地数据库，分别执行两份迁移（只执行一次）：

```sh
node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0000_tough_shadow_king.sql
node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0001_outstanding_the_professor.sql
npm run dev -- --port 5178 --hostname 127.0.0.1
```

已有初始演示数据库时，只执行尚未应用的第二份迁移。旧表保持原样，M1 使用新的 `catalog_workspaces` 表，应用不读取旧演示数据。迁移再次执行会报告表已存在，不要为了重跑删除已有业务数据。

已有唯一货盘时自动沿用；不会改变管理员、商户或供货归属。若存在多份历史货盘，管理员须通过服务器环境变量 `SHANHAI_WORKSPACE_ID` 指定本平台货盘，系统不自动合并或删除旧数据。此变量不能来自浏览器请求。

新空数据库执行上述迁移后，由有部署权限的管理员初始化一次：

```sh
npm run platform:setup -- --owner-id <可信登录系统中的管理员用户ID>
```

该脚本仅操作本地 D1，且只在货盘表为空时插入；重复执行不会覆盖已有数据或更换负责人。管理员用户 ID 必须来自实际部署的可信登录身份，不能使用显示名称或从商户提交的表单取值。云端初始化需部署人员通过受控数据库操作完成同等初始化，浏览器 API 没有初始化功能。

打开 `http://127.0.0.1:5178/merchant/login` 或 `http://127.0.0.1:5178/operations/login`。当前 Sites 本地登录固定为一个开发账号；多账号入驻和访问隔离通过 SQLite 接口测试验证。正式试用还需确定面向商户的登录方式和站点访问策略。

## 检查

```sh
npm run check
npm test
npm run build
npm run test:api
```

`test:api` 需要先启动本地服务，并有已初始化、开发账号具备运营权限的本地平台。验证双登录页、匿名跳转、角色引导和关闭自建空间接口，再新增标注的测试商户、商品和供货记录，并上传一张1像素 PNG 到本地 R2。同时验证专属邀请生成、读取及撤销。验证完成将测试报价暂停、测试邀请撤销，不编辑现有商户的供货、不对外发送消息。其余检查不需要外部服务或密钥。

测试使用 Node 内置测试框架；接口测试通过 SQLite 执行与 D1 相同的查询，覆盖入驻、权限隔离、报价版本、并发冲突和过期规则。CI 在每次推送和 PR 时执行类型检查、测试与构建，实际运行结果见 [GitHub Actions](https://github.com/nredcolon/altitude-supply/actions)。

| 路径 | 用途 |

## 当前限制

- 当前实现为 M1 开发里程碑，尚未上线。海外选品、自动匹配和对外报价分别属于 B1、M2、M3。
- 登录沿用 Sites/ChatGPT 身份入口，应用层已实现统一平台内的管理员、运营和商户归属。迁移至其他托管平台需要替换身份适配器；不能直接信任来自公网客户端的身份头。
- 商户自助申请及代录档案认领已实现；认领需运营通过原登记联系人线下核实，不能仅凭申请人自填联系方式确认。尚不支持已绑定账号的更换、负责人转移或细分运营角色。准入与登录体验需用实际商户验证。
- 商品图片支持本地预览 R2 上传及 HTTPS 地址；需要 `BUCKET` 绑定，已在源配置中声明。云端资源尚未部署验证。批量导入及审核材料附件尚未实现。
- 图片上传成功但表单取消时可能留下未关联图片；后续增加安全清理任务。海外选品端需要独立公开图片发布流程，不能直接绕过内部图片权限。
- 标准 SKU 审核后不修改商品身份；发生规格变化应新建 SKU。误关联的合并、重关联和历史迁移属于后续数据治理任务。
- 每个空间目前以一个带版本号的 JSON 聚合存入 D1，约 2 MB 保存上限，适合小范围验证；扩量前拆分表、分页和独立审计归档。
- 暂不做采购承诺、数量预占、外部支付、物流操作或任何自动消息发送。
